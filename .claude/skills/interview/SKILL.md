# /interview

NEXTSTEP "나만의 Claude OS 만들기" 2주차 PRACTICE(`2주차.pdf` p28–31 "의도 추출 · 모호함 문제")의 산출물.

> **목표(p31)**: 코드는 AI가 만들어주는 시대 — **나만의 철학을 투영하는** 인터뷰 스킬.
> 모호한 의도(INPUT) → 반복적 Q&A → 구체화된 의도(OUTPUT). (p29)

이 스킬은 "로그인을 만들어줘" 같은 모호한 요청을 받았을 때, **복불복으로 추측해서 실행하지 않고**(p28) 먼저 무엇이 비었는지 측정하고, 빈 곳만 골라 묻는다.

## 0) 이 스킬의 철학 — 왜 이 6축인가

이 저장소 소유자(jaenyeong)의 **실제 과거 프롬프트 50여 개를 분석**해서, 반복적으로 비는 자리를 6개 축으로 박제했다. 즉 일반론이 아니라 *이 사람이 실제로 모호하게 던지는 패턴*에 맞춰져 있다.

| 축 | 묻는 것 | 이 사람의 실제 약점 신호 (과거 프롬프트에서) |
|---|---|---|
| **Goal** 의도 | 최종적으로 뭘 달성? | "이게 맞다면…", "방향과 일치하는지 확인해줄래?" (목표 미확정 채로 시작) |
| **Scope** 범위 | 단일 작업인가, 여러 개 묶였나? 어디까지? | "그리고… 그리고…" — **한 메시지에 2~4개 작업 번들링** (최대 약점) |
| **Actor** 주체 | 누가 수행/검증/판단? | "성능은 **누가** 체크?", "스펙은 **누가** 확인?", "위치는 **누가** 해?" (역할 누락 반복) |
| **Done** 완료조건 | 산출물 포맷·통과 기준은? | "작업한 내용을 커밋해" (단위·기준 없음) |
| **Autonomy** 자율성 | 어디까지 알아서, 어디서 멈춰 물을지? | "알아서 …하던지" + "최종 컨펌만 받아" + "맘대로 하지말고" (경계 모호) |
| **Constraints** 제약 | 컨벤션·정책·기술 제약? | 보통 충족됨 (CLAUDE.md·rules에 박제돼 있어 자동 주입) |

## 1) 동작 원리 — 신호등 게이트

모호함은 **단일 점수가 아니라 "어느 축의 신뢰도가 낮은가"** 로 본다. 그래야 측정이 곧바로 행동(질문)으로 이어진다.

각 축마다 다음을 자문한다 — **"나는 추측 없이 이 축을 실행할 수 있는가?"**

- 🟢 **High** — 추측 불필요. 명시됐거나 컨텍스트(CLAUDE.md/rules)로 확정됨 → 질문 안 함
- 🟡 **Med** — 합리적 기본값은 있으나 갈릴 수 있음 → 질문함 (기본값을 후보로 제시)
- 🔴 **Low** — 추측하면 복불복 → **반드시 질문**

> **게이트 규칙**: 🔴 또는 🟡 인 축이 **하나라도** 있으면 인터뷰에 진입한다. 전부 🟢 면 인터뷰를 건너뛰고 바로 실행 의도로 넘긴다. (모호하면 묻고, 명확하면 안 묻는다)

## 2) STEP 1 — 의도 분해 (번들 풀기)

가장 먼저, 요청에 **여러 작업이 묶여 있는지** 본다. 이 사람의 1순위 약점이다.

- `그리고` / 줄바꿈 / "~도", "~까지" 로 연결된 독립 작업을 **목록으로 분리**한다.
- 분리된 각 작업이 **이번 스코프인지(now) / 나중인지(later) / 곁다리 질문인지(aside)** 를 표시한다.
- 메인 작업 1개를 정하고, 나머지는 사용자에게 "이것도 이번에 같이 할까요?"로 확인 대상에 올린다.

출력 예:
```
의도 분해:
  [main]  PR 리뷰 오케스트레이터 만들기
  [now?]  의사결정 질문 에이전트 포함
  [later] 사이드이펙트 검사 에이전트
  [aside] "이건 코드 리뷰어인가?" ← 용어 확인 질문
```

## 3) STEP 2 — 6축 신호등 스코어링

분해된 **메인 의도**에 대해 6축을 각각 🟢/🟡/🔴 로 판정하고 표로 보여준다. 판정 근거를 한 줄씩 단다.

```
Goal      🟢  "PR 리뷰 자동화"로 명확
Scope     🔴  리뷰 대상이 신규구현/리팩터/남의PR 중 무엇인지 불명
Actor     🔴  어떤 리뷰어(code/security/test/spec)들이 참여하는지 미정
Done      🟡  리포트 산출은 알겠으나 통과 기준/라운드 수 미정
Autonomy  🟢  "결정 필요한 부분은 물어봐"로 명시됨
Constr.   🟢  커밋컨벤션·계정정책은 CLAUDE.md에 박제
→ 🔴2 🟡1 : 인터뷰 진입 (3개 축만 질문)
```

## 4) STEP 3 — 부족한 축만 객관식으로 질문

🔴·🟡 축에 대해서만 **`AskUserQuestion` 도구로 선택지형 질문**을 던진다. (이 사람은 객관식으로 답하는 걸 선호 — 모호한 상태에서 방향 잡기 쉬움)

질문 작성 규칙:
- **한 번에 최대 3~4개 축**만. 더 많으면 라운드를 나눈다 (`실습 전 최대 2-3개` 원칙, p30).
- 각 축당 2~4개의 **구체적 후보**를 제시한다. 추측 가능한 합리적 기본값은 첫 번째 옵션에 두고 `(권장)`을 붙인다.
- 옵션은 서로 **배타적**이고 결정을 실제로 바꾸는 것이어야 한다. "예/아니오" 수준의 빈 질문 금지.
- 사용자가 "Other"로 자유 입력할 수 있음을 신뢰한다.
- 답이 들어오면 해당 축을 🟢 로 갱신하고, 남은 🔴·🟡 가 있으면 다음 라운드. **모든 축이 🟢 가 되면 종료.**

### 구체화 영역 — 질문을 만들 때 참고하는 6개 영역

질문 후보를 떠올릴 때 아래 영역을 체크리스트로 쓴다. 앞 3개는 **기술 산출물**, 뒤 3개는 **프로세스/메타**(이 사람이 자주 빠뜨리는 쪽).

1. **아키텍처 디자인** — 모듈 경계, 레이어, 의존 방향, 확장 포인트
2. **코드 레벨 구조 설계** — 클래스/패키지 위치, OOP/FP 패러다임, DTO 위치 등 (→ `kotlin-style.md` 참조)
3. **도메인 요구사항** — 비즈니스 규칙, 엣지 케이스, 감사(actorId) 등 도메인 정책
4. **역할·위임 (Actor/Orchestration)** — 누가 수행/리뷰/검증/판단하는가 *(가장 자주 누락)*
5. **완료조건·산출물 (Deliverable)** — 데이터 타입/포맷, ADR·PRD 문서, 통과 기준
6. **자율성·게이트 (Autonomy)** — 어디까지 자율 실행, 어디서 멈춰 컨펌받는가

## 5) STEP 4 — 구체화된 의도 산출 (OUTPUT)

모든 축이 🟢 가 되면, 추측이 제거된 **실행 가능한 명세**로 정리해 보여주고 최종 확인을 받는다.

```markdown
## 구체화된 의도

- **Goal**: …
- **Scope (now)**: …  / (later) …
- **Actor**: … 가 수행, … 가 검증
- **Done**: 산출물=…(포맷), 통과기준=…
- **Autonomy**: …까지 자율, …에서 컨펌
- **Constraints**: … (CLAUDE.md/rules 준수)
```

확인 후의 다음 행보(이 스킬은 **여기서 멈추고 사용자 확인을 받는다**):
- 그대로 실행하거나,
- `/review-pr` 같은 상위 파이프라인 스킬에 이 명세를 넘기거나,
- 명세가 재사용 가치가 있으면 "이걸 새 스킬로 박제할까요?"를 제안한다 (p31의 "인터뷰 후 스킬 생성").

## 6) 경계 — 하지 않는 것

- 의도가 이미 6축 모두 🟢 면 **질문하지 않는다.** 불필요한 인터뷰는 그 자체로 컨텍스트 오염(Context Rot, p34).
- 답을 강요하지 않는다 — 사용자가 "알아서 해"라고 하면 Autonomy 축을 High로 두고 합리적 기본값으로 진행.
- 코드를 작성하거나 커밋하지 않는다. 이 스킬의 산출물은 **구체화된 의도(명세)** 까지다.
